## 1. Public C4 transport must preserve the controlled causal interface

The ordinary public main table remains an end-to-end method comparison. It is not itself the causal transport estimand.

For the separately reported C4 transport object, eligibility must be determined prospectively from pre-treatment observables. For every eligible natural unit, freeze before either learner-projection arm is materialized:

- one common starting persistent state;
- one common realized search/evidence object;
- one common served winner/action and serving-side behavior;
- the same target/future task and evaluator;
- the same executor/updater family, budgets, context renderer, preprocessing, and randomization contract.

Construct both learner projections from that exact same frozen realized object. Only the learner projection `g(T_K)` may differ.

The paired public transport contrast is therefore:

`Delta_transport,m = (FF4_Typed_m - FF4_Free_m) - (WIN_Typed_m - WIN_Free_m)`

or the exact public-compatible projection names frozen at C0, provided the 2x2 retains the same meaning: evidence source / learner projection crossed on a common realized object with serving fixed.

A positive end-to-end method difference without this matched object is policy-performance evidence, not transport of the controlled B2 causal interface.

### C4 validity gate

C4 is invalid/blocked if any eligible pair differs before learner projection in starting state, realized evidence/search object, served action, evaluator, context/preprocessing, or budget. No post-outcome matching or replacement is allowed.

## 2. Public split and leakage contract

The public SpreadsheetBench Verified-400 lane freezes the released `80 / 40 / 280` train/evolution / validation / test structure at C0, or an exactly audited deterministic equivalent if the released manifest itself cannot be used.

Requirements before public execution:

- exact task/workbook/version hashes;
- exact ordering and split manifest;
- explicit group/duplicate leakage audit at the semantic unit used by the benchmark;
- public test units never enter evolution, calibration, threshold selection, prompt tuning, compiler vocabulary design, model selection, or method/baseline debugging;
- validation may select only prospectively declared execution parameters; it may not modify the scientific estimand or method semantics;
- no public outcome is used to alter the already frozen controlled M2/M3R4/M4 objects.

If fewer than 20 eligible primary C4 pairs survive prospectively frozen qualification, C4 is reported as supportive transport evidence rather than confirmatory transport evidence. No outcome-conditioned top-up is permitted.

## 3. Corpus and comparator parity

Before any baseline/public execution, freeze for every method:

- exact corpus source and revision;
- exact deduplication key/granularity and normalization;
- source-license/access class and whether redistribution is permitted;
- exact task IDs available to evolution, validation, and final test;
- no test-to-train retrieval/index leakage;
- comparator implementation source/revision and legal execution surface;
- per-method context construction/preprocessing.

Cross-model byte identity is not required. Within a given model, the primary method and comparator must receive identical non-treatment context, preprocessing, task inputs, budgets, and evaluator. No model-conditioned filtering of difficult tasks or units is allowed.

If a literature comparator cannot legally or technically run under a matched information/budget surface, report it as unavailable/incomparable rather than silently weakening its contract.

## 4. Full-evolution replication for stochastic methods

Heldout-panel repeats measure downstream evaluation/execution noise; they do not replace independent evolution realizations.

For every method, classify the full evolution pipeline prospectively:

### Deterministic evolution
One evolution realization is sufficient only if all evolution randomness is fully pinned and repeated execution is byte/identity reproducible under the frozen environment.

### Stochastic evolution
If any updater/reflection/candidate-generation/validation-selection/evolution-history randomness remains provider- or process-stochastic, use exactly three common paired full-evolution seeds/realizations as the minimum publication contract.

For each stochastic method report:

- per-seed evolved-state identity/hash where meaningful;
- between-evolution-seed variation in downstream utility;
- within-evolved-state heldout/evaluation repeat variation separately;
- a nested summary that does not count heldout repeats as independent evolution units.

The three-seed rule is a minimum robustness contract, not a request for a seed sweep. A failed seed is retained under the frozen failure policy; no reroll to obtain three favorable states.

## 5. Frontend / reader-facing claim semantics

The following wording is forbidden unless a later experiment identifies a broader optimization problem:

- `best to act != best to learn`
- `best to learn`
- any implication that the experiment searches over all learner projections.

Preferred causal wording:

> With the served winner held fixed, does retaining an alternative projection of the same realized search evidence improve future learning relative to winner-coupled learning?

If B2/B3 pass across all five preregistered procedural skeletons, the strongest allowed finite-suite statement is:

> With serving fixed, the prospectively frozen alternative learner projection outperformed WIN-C learning across the five preregistered procedural skeletons.

Reader-facing UI should use `fresh qualification gate`, `execution gate`, or `status flag`, not `authority gate`, unless the element is literally an authorization object.

Replace broad lifecycle language such as `updated only after execution and evaluation` with the narrower causal constraint:

> The learner must not update from the current task outcome before the serving action/trajectory being evaluated is complete.

The public anchor must say `Universal MRW4 or prospectively frozen public-compatible alternative`, not unconditional MRW4 compatibility.
